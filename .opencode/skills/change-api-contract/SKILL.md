# API 계약 바꾸기

계약 원본은 세 레포 공통 문서의 `03-api-contract.md`다. 이 레포의 `docs/contract/api-contract.md`는 **복사본**이다.
복사본만 고치면 다른 두 레포와 어긋난다.

## 절차
1. **바꿀 내용을 한 문단으로 적는다**: 무엇을(경로·필드·이벤트·열거형), 왜, 바뀌는 JSON 예시(전·후), 어느 레포가 영향받는지.
2. **호환되게 바꿀 수 있는지 본다.** 될 수 있으면 "더하기"로 한다.
   - 필드 추가(선택 값) → 호환. 받는 쪽은 없는 필드를 견뎌야 한다.
   - 필드 이름 변경·삭제, 열거형 값 삭제, 필수 값 추가 → 깨짐. 아래 "배포 순서"의 세 단계로 한다.
3. **세 레포 담당이 합의한다.** 합의 전에는 코드를 고치지 않는다.
4. **원본을 고치고, 같은 날 세 레포의 복사본(`docs/contract/api-contract.md`)을 같은 내용으로 덮어쓴다.** 표와 JSON 예시를 둘 다 고친다.
5. **이 레포의 코드를 맞춘다**:
   - REST: `src/api/index.js`, `src/mocks/server.js`, 쓰는 화면
   - WebSocket 이벤트: `src/features/room/room-state.js`(+ `room-state.test.js`), `src/mocks/socket.js`
   - 열거형: `src/lib/labels.js`
6. **PR 설명 맨 위에 `[계약 변경]`을 적고**, 고친 계약 문서의 diff를 그대로 붙인다.

## 배포 순서 (세 레포 공통)

이 문단은 세 레포의 `change-api-contract` skill에 같은 내용으로 들어 있다. 고칠 때는 셋을 함께 고친다.

- **더하는 변경**(필드·경로·이벤트·오류 코드 추가): 어느 쪽이 먼저 나가도 되게 만든다. 받는 쪽은 그 값이 **없어도** 동작하고, **모르는 값이 와도** 무시한다. 그래도 순서를 정해야 하면 내보내는 쪽이 먼저다.
- **깨는 변경**(이름 변경, 삭제, 타입 변경, 필수화, 뜻 변경): 한 번에 바꾸지 않는다. 추가 → 옮기기 → 삭제 세 단계로 한다. 받는 쪽이 먼저 옛것과 새것을 모두 받게 하고, 그다음 보내는 쪽이 새것으로 바꾸고, 마지막에 옛것을 지운다.
- **열거형 값 추가**는 깨질 수 있다. 받는 쪽이 모르는 값을 받아도 죽지 않는지 먼저 확인한다.
- 계약 문서(원본과 세 복사본)는 같은 날 고친다. 코드는 위 순서를 지키면 같은 날이 아니어도 된다.

## 혼자 세 레포를 다 볼 수 있을 때
세 레포가 같은 상위 폴더에 있으면 원본과 복사본 세 개를 한 번에 같은 내용으로 고치고, 레포마다 PR을 만든다. 네 파일의 내용이 같은지 마지막에 비교한다.

## 하지 말 것
- 화면에 필요하다고 mock에만 필드를 더하기(실서버에 붙이면 깨진다)
- 계약 문서를 안 고치고 코드만 바꾸기
- 이 레포의 복사본만 고치기
